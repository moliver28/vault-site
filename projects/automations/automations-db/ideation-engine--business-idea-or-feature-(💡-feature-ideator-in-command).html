Ideation Engine: Business Idea or Feature (💡 Feature Ideator in command)

Mar 15, 202615 min read

💡 Feature Ideator must be loaded to perform this automation {color=“red_bg”}

### Dual-Mode Automation Determine from user intent or ask which mode to run: **Mode A — Ideate Business Idea:** Generate business concepts from persona, JTBD, or market context. Output → new page in with Status: Idea. **Mode B — Ideate Feature Idea:** Generate feature concepts for an existing business idea. Output → `💡 Feature Concepts` subpage under the parent page. ### Market-First Principle By default, this automation ideates based on **market opportunity and user needs only**. The operator's personal skills, knowledge, and network () are **NOT loaded and must NOT constrain ideation**. Do not factor in what the operator can personally build, knows, or has access to unless explicitly activated via the **Founder-Fit Overlay** (see below). This ensures the widest possible solution space. ### Chained Automations ⬆️ **Upstream:** - Persist Persona Shortlist to Project (Analyst in command) (reads Active personas from Project page) - Identify Market Populations to Innovate For (🧭 Market Population Identifier in command) (direct handoff from Phase 8 with proto-persona) - Market Evaluation Scoring Kit (handoff with scored population and Kano landscape) - Validate Business Idea (handoff with validated persona, JTBD insights, and problem space — Mode B typical) - Can also be triggered standalone with any persona/JTBD input ⬇️ **Downstream:** - **Mode A →** Validate Business Idea (stress-test the top ideated concept) - **Mode B →** None (terminal output; feature concepts subpage is the deliverable) 🔄 **Handoff type:** `gated` (each upstream handoff pauses for user confirmation before this automation begins) --- **Handoff Contracts:** **⬆️ From Identify Market Populations (direct)** - **Trigger:** User confirms Ideation handoff at Identify Market Phase 8 - **Payload received:** Proto-persona (Who/What/Why/Where) from ranked shortlist - **Validation gate:** Proto-persona has all four dimensions populated **⬆️ From Market Evaluation Scoring Kit** - **Trigger:** User confirms Ideation handoff after Market Eval scoring - **Payload received:** Proto-persona enriched with evidence classifications and Kano landscape - **Validation gate:** Proto-persona has all four dimensions; scoring data present **⬆️ From Validate Business Idea (Mode B typical)** - **Trigger:** User confirms Feature Ideation handoff after Phase 4 documentation - **Payload received:** Target user persona (Who/What/Why/Where), JTBD insights (functional/emotional/social jobs), validated problem space, Business Ideas DB page URL - **Validation gate:** Business Ideas DB page created; target user persona complete **Mode A → Validate Business Idea** - **Trigger:** User confirms Validate handoff after business idea is persisted - **Payload:** Business Ideas DB page URL, persona, JTBD decomposition, needs analysis - **Validation gate:** Business Ideas DB page created with Status: Idea **Full possible chain (all steps optional, user chooses path):** Identify Market → Market Eval → **Ideation Engine (Mode A)** → Validate Business → **Ideation Engine (Mode B)** → Feature Concepts subpage Each handoff is gated. The user may enter at any point or skip any intermediate step. ### INPUT **Mode A — Ideate Business Idea:** - **Required:** A user persona containing at minimum Who, What, Why, Where/When - **Optional:** JTBD statement in format: "When \[situation\], I want to \[motivation\], so I can \[outcome\]" - **Optional:** Domain context, competitive landscape, upstream Market Scan or Market Eval data **⚠️ NOT loaded by default:** , personal skills, knowledge, or network constraints. See **Founder-Fit Overlay** section below. **Mode B — Ideate Feature Idea:** - **Required:** An existing page (the parent business idea to generate features for) - **Optional:** Additional persona detail, JTBD statement, technical constraints - **Auto-loaded from parent page:** Target User, Problem Statement, Validation Score, and any page content (validation answers, scoring, etc.) **⚠️ NOT loaded by default:** , personal skills, knowledge, or network constraints. See **Founder-Fit Overlay** section below. ### STEPS ## Phase 0: Mode Selection & Context Loading 1. **Determine mode** from user intent: - "ideate a business idea," "brainstorm business concepts," persona/market context without an existing idea → **Mode A** - "ideate features for \[idea\]," "what features should we build," referencing an existing Business Ideas DB page → **Mode B** - If ambiguous, ask: *"Do you want to ideate a new business idea (Mode A) or ideate features for an existing one (Mode B)?"* 2. **Load context from :** - Ask: *"Is this tied to an existing idea in Business Ideas DB?"* (or infer from context). - **Mode B (required):** Load the Business Ideas DB page. Extract Target User, Problem Statement, and existing page content as input context for Phases 1-5. - **Mode A (optional):** If upstream data is available (Market Scan, Market Eval scoring, validated persona), load it as supplementary context. - If the user names a specific idea, query to locate it. 3. **Founder-Fit Overlay (optional):** Ask: *"Do you want to apply a Founder-Fit lens using your Means Inventory?"* If yes, load and activate the Founder-Fit Overlay after Phase 6. If no (or if the user doesn't mention it), proceed without any personal skills constraints. **Default: No.** ## Phase 1: Input Validation (MANDATORY GATE) — Both Modes 1. Restate the persona in a structured summary. Confirm you have Who/What/Why/Where. 2. If any dimension is missing or thin, STOP and ask clarifying questions. Do NOT proceed with incomplete input. 3. If a JTBD statement is provided, decompose it into Functional Job, Emotional Job, and Social Job. 4. If no JTBD is provided, infer the primary functional job from the persona's goals and flag this as an assumption. 5. **Mode B only:** Confirm the parent Business Ideas DB page and summarize the existing idea context (Problem Statement, Target User, Validation Score, any scoring data). ## Phase 2: Needs Decomposition — Both Modes 1. Extract **Explicit Needs**: directly stated goals, pain points, desired outcomes from the persona. 2. Infer **Implicit Needs**: what the persona's context, environment, and workflow patterns reveal about unstated requirements. 3. Infer **Latent Needs**: what the persona cannot articulate but would value. Use means-end laddering (attribute → functional consequence → psychosocial consequence → personal value) to surface motivational depth. Justify each latent need with explicit reasoning. 4. Identify **AI-Discoverable Latent Needs**: needs that were invisible to incumbents because the relevant evidence was locked in fragmented or proprietary sources — support tickets, community workarounds, telemetry, peer-to-peer conversations, abandoned-feature data, public review corpora, niche forum threads. For each, name the data source, the unmet need it implies, and whether modern AI is what newly makes the analysis tractable. The most valuable 2026 opportunities sit here. 5. Present the Needs Decomposition Table (4 layers: explicit / implicit / latent / AI-discoverable) to the user for review before proceeding. ## Phase 3: HMW Reframing — Both Modes 1. Convert each validated need into a "How Might We \[verb\] \[user's need\] so that \[desired outcome\]?" prompt. 2. Ensure each HMW constrains to the problem space but opens the solution space. 3. Group HMW prompts by need layer (explicit → implicit → latent). ## Phase 4: Divergent Ideation ### Mode A — Business Idea Concepts For each HMW prompt, generate 3-5 **business concepts**. Each concept includes: - **Value Proposition:** What unique value does this deliver to the target user? - **Business Model Sketch:** Revenue model, pricing signal, unit economics hypothesis - **Differentiation Angle:** Why incumbents can't easily replicate this - **Entry Wedge:** Smallest viable starting point to test the concept Use seven lenses: - **Analogous Inspiration:** What do adjacent domains do for similar needs? - **Constraint Removal:** What if we removed the biggest barrier? - **Extreme User Thinking:** What would the most demanding user need? - **Technology Leverage:** What emerging capabilities could address this? - **Inversion:** What would the *opposite* design choice look like, and who would prefer it? What if the feature everyone defaults to were removed? - **Micro-JTBD & Ecosystem Stitching:** Decompose the main job into atomic micro-jobs. For each, ask: *can solving this micro-job for two distinct user types create a peer-to-peer surface (templates exchange, peer review, expert directory, community Q&A, marketplace seed) that satisfies an unmet relational need?* Concepts that connect end-users to each other are network-effect candidates and graduate faster up the Zero-to-TAM Staircase. - **AI Opportunity Classifier:** Tag every concept as **Cheap-with-AI** (existed, AI collapsed cost), **Only-AI-Can-Do** (infeasible before modern models), **AI-Discoverable Need** (need newly visible via AI synthesis of fragmented data), or **AI-Optional** (no AI value). The first three carry asymmetric-advantage windows; AI-Optional concepts must justify differentiation independent of AI. ### Mode B — Feature Concepts For each HMW prompt, generate 3-5 **feature concepts** using the same seven lenses. Each feature concept must include: Name, Description, Source HMW, and the means-end chain it serves. ## Phase 5: Convergent Classification ### Mode A — Business Idea Ranking Lightweight viability screen (NOT full Validate Business Idea scoring — that comes downstream if the user chooses):
DimensionRatingWhat You're Assessing
**Problem-Solution Fit**H / M / LDoes this concept directly address the decomposed needs?
**Differentiation Strength**H / M / LIs the angle defensible or easily copied?
**Feasibility**H / M / LCan this be built/delivered with reasonable resources by a competent team? (Market-general — do NOT constrain to operator's personal skills.)
**Market Signal**H / M / LIs there evidence of demand beyond assumption?
**Pivot-Readiness Annotation (mandatory):** for each concept, name the 1–2 most plausible Ries pivots if the riskiest assumption fails (zoom-in, zoom-out, customer-segment, customer-need, platform, business-architecture, value-capture, engine-of-growth, channel, technology). Concepts with zero plausible pivots are dead-end concepts and must be flagged. **Zero-to-TAM Staircase Position:** for each concept, name the entry step (0–4) from §11 (Zero-to-TAM Staircase), plus the Step 1 → Step 2 climb signal that would justify expansion. **Network-Effect Potential rating:** Compounding (P2P core), Adjacent (network is reachable but not the wedge), or None. Rank concepts by composite strength. Present top 3 with full concept cards. ### Mode B — Feature Classification 1. **Kano Classify** each feature: - **Must-Be**: Expected baseline. Absence causes dissatisfaction, presence is neutral. - **Performance**: Linear satisfaction. More/better = more satisfaction. - **Attractive (Delighter)**: Unexpected value. Absence is neutral, presence delights. 2. **TAM Pre-Validate** each feature: - Perceived Usefulness (PU): High / Medium / Low - Perceived Ease of Use (PEOU): High / Medium / Low - Adoption Likelihood = PU × PEOU. Flag any feature with Low on either dimension. ## Phase 6: Output Assembly ### Mode A Deliverable 1. **Persona Summary** (restated, structured) 2. **JTBD Decomposition** (functional / emotional / social jobs) 3. **Needs Decomposition Table** (explicit / implicit / latent / AI-discoverable, with evidence, means-end chains, and named data sources for the AI-discoverable layer) 4. **HMW Prompts** (numbered, grouped by need layer) 5. **Business Concept Cards** (top 3-5 ranked concepts with value prop, model sketch, differentiation, entry wedge, viability rating, **AI Opportunity Classification**, **Pivot-Readiness map** with 1–2 plausible Ries pivots, **Zero-to-TAM Staircase entry step**, and **Network-Effect Potential rating**) 6. **Viability Ranking** (composite rationale) 7. **Methodological Limitations** (assumptions, what would strengthen validation) ### Mode B Deliverable 1. **Persona Summary** (restated, structured) 2. **JTBD Decomposition** (if provided: functional / emotional / social jobs) 3. **Needs Decomposition Table** (explicit / implicit / latent / AI-discoverable, with evidence, means-end chains, and named data sources for the AI-discoverable layer) 4. **HMW Prompts** (numbered, grouped by need layer, linked to source needs) 5. **Feature Concept Cards** for each feature: - Name and description - Source HMW prompt - Kano Category (Must-Be / Performance / Attractive) - TAM Scores (PU: H/M/L, PEOU: H/M/L, Adoption Likelihood) - Means-End Chain (attribute → consequence → value) 6. **Priority Matrix** (ranked list with composite rationale) 7. **Methodological Limitations** (assumptions, what would strengthen validation) --- ## Persist to Business Ideas DB **Artifact Layout (Mode A only):** Create the page per the . Seed the Live Synthesis skeleton (Verdict shell plus the section headers, high to low) and open the first dated Appendix entry with the Mode A deliverable (concept cards, needs decomposition). Mode B is unchanged: feature concepts stay a subpage and never modify the parent page. ### Mode A — Create Business Ideas DB Page 1. **Create a page** in : - **Idea Name:** Clear, descriptive title for the top-ranked concept - **Status:** "Idea" - **Problem Statement:** Synthesized from Needs Decomposition - **Target User:** From persona input - **Tags:** Most appropriate category 2. **Page content:** Full Mode A deliverable from Phase 6. 3. **Multiple concepts:** If more than one strong concept, create one page per concept (confirm count with user). 4. **Downstream offer:** *"Want to run Validate Business Idea to stress-test this concept?"* ### Mode B — Create Feature Concepts Subpage 1. **Create a subpage** titled `💡 Feature Concepts` **under the parent Business Ideas DB page.** 2. **Subpage content:** Full Mode B deliverable from Phase 6. 3. **NEVER modify existing content** on the parent Business Ideas DB page. 4. **Re-run behavior:** If a `💡 Feature Concepts` subpage already exists under the parent page, replace its content (not the parent page). **NEVER overwrite or modify the parent Business Ideas DB page content.** Feature concepts are always a subpage, never appended to or merged into the parent page. --- ## Persona Slate Offer After output is complete and before closing: *"Would you like to build the full stress-test persona slate (your input persona + 💼 Zero-Tech Investor + 😈 Contrarian Antagonist) and persist it to a Project page?"* If yes, hand off to Infer Persona Slate (Analyst in command) with `context = ideation_engine`, the persona used for ideation as `anchor_personas`, and the Business Ideas DB page URL as `source_url`. That automation builds the stress-test slate (🏛️ Architectural CTO is intentionally skipped at the ideation stage; it rejoins downstream when a technical plan exists) and writes the `🎯 Persona Shortlist` section directly into the Business Ideas DB page itself. --- ## Optional: Founder-Fit Overlay **Activated ONLY when the user explicitly requests it.** DO NOT activate by default. DO NOT load unless this overlay is active. When activated, load and append a **Founder-Fit Analysis** section to the output (after all market-based analysis is complete): 1. **Skills Alignment:** Which concepts align with the operator's core expertise and abstracted skill patterns? 2. **Network Leverage:** Which concepts benefit from the operator's strong/moderate access networks? 3. **Resource Reality Check:** Given the operator's time, budget, and team constraints, which concepts are personally executable vs. requiring partners/hires? 4. **Founder-Fit Rating:** H / M / L for each concept ⚠️ **This section is informational only.** Founder-Fit ratings must NEVER retroactively change the viability ranking, Kano classifications, TAM scores, or any other market-based assessment from Phases 1-6. It is a **separate lens** applied after the market-first analysis is complete. --- ### Rules - **NEVER** skip Needs Decomposition. Every concept (business or feature) must trace to a decomposed need. - **Mode B: NEVER** present features without both Kano classification AND TAM pre-validation. - **NEVER** ideate from thin input. If the persona is vague, ask for more before generating. - **ALWAYS** distinguish between explicit, implicit, and latent needs with clear evidence. - **ALWAYS** flag latent needs as inferred with reasoning. - **ALWAYS** use validated HCI terminology (Contextual Design, Kano Model, TAM, HMW, Laddering). - **ALWAYS** present Needs Decomposition for user review before ideation phases. - **ALWAYS** persist output to (Mode A: new page; Mode B: subpage of parent). - If the user provides competitive context, use it to calibrate classifications (what competitors offer shifts features toward Must-Be). - If the user provides technical constraints, use them to adjust feasibility ratings. - **NEVER** load or factor personal skills, knowledge, or network into ideation unless the user explicitly requests the Founder-Fit Overlay. - **NEVER** constrain the solution space to what the operator can personally build, knows, or has access to. Ideation is market-first by default. - **NEVER** let Founder-Fit analysis retroactively alter market-based scores or rankings. - **ALWAYS** include the AI-Discoverable Latent Needs layer in Needs Decomposition. The most valuable opportunities in 2026 are needs AI now makes legible from previously fragmented data. - **ALWAYS** tag every business or feature concept with the AI Opportunity Classifier (Cheap-with-AI / Only-AI-Can-Do / AI-Discoverable Need / AI-Optional). Concepts tagged AI-Optional must justify differentiation independent of AI. - **ALWAYS** annotate every concept with at least one plausible Ries pivot. Concepts with no plausible pivot are dead-end concepts. - **ALWAYS** name the entry step (0–4) on the GTM Build-Now Inventory §11 Zero-to-TAM Staircase for every concept. - **ALWAYS** apply the Micro-JTBD & Ecosystem Stitching lens to surface end-user-to-end-user (peer) angles. Network-effect candidates get a Compounding / Adjacent / None rating in the output. ### Framework Reference Links These sources ground each pipeline step in validated academic and practitioner literature.
