Architecture Reference

Nov 13, 202611 min read

**Reference documentation for multi-agent system design patterns.** This page contains **theoretical patterns and schemas for future systems**, not current runtime behavior. The actual system is a single reasoning loop that loads instruction sets on demand. For how the system actually works, see Meta-Agent Master Prompt. ### 🚧 Historical Context This document was written when the architecture aspired to true multi-agent orchestration. The current implementation is simpler and more honest: **one reasoning loop, multiple instruction sets**. Keep this doc for: - Design pattern reference if building more complex systems later - Understanding the evolution of the architecture - Concepts that still apply (memory via pages, context via sync blocks) --- ## 🏠️ Orchestration Topologies ### Router Pattern **When to use:** Task requires dynamic dispatch based on input classification ```javascript 🎯 Router Agent ├── Classifies incoming request ├── Routes to specialist agent └── Collects and returns result ``` **Notion Implementation:** - Router page with classification logic in System Prompt - Specialist agents as child pages - State Machine with branching transitions - Single sync block from Router → all specialists ### Planner Pattern **When to use:** Complex tasks requiring decomposition and sequencing ```javascript 📝 Planner Agent ├── Decomposes goal into subtasks ├── Creates execution plan ├── Assigns to executor agents └── Monitors completion ``` **Notion Implementation:** - Planner creates task entries in Execution Log - Each subtask becomes a State in State Machine - Executor agents subscribe via sync blocks - Plan stored in Agent Memory (Long-term) ### Hierarchical Pattern **When to use:** Tasks with natural parent-child decomposition ```javascript 👑 Supervisor Agent ├── 👷 Manager A │ ├── 🧑‍💻 Worker A1 │ └── 🧑‍💻 Worker A2 └── 👷 Manager B ├── 🧑‍💻 Worker B1 └── 🧑‍💻 Worker B2 ``` **Notion Implementation:** - Nested page structure mirrors hierarchy - Parent sync blocks cascade to children - Each level has filtered database views - Dependencies relation creates the tree ### Swarm Pattern **When to use:** Embarrassingly parallel tasks, consensus building ```javascript 🐝 Swarm Coordinator ├── 🐜 Agent 1 (parallel) ├── 🐜 Agent 2 (parallel) ├── 🐜 Agent 3 (parallel) └── 🪹 Aggregator (waits for all) ``` **Notion Implementation:** - Coordinator spawns parallel State entries - All swarm agents share same input sync block - Each writes to individual output sync block - Aggregator embeds ALL output sync blocks - Forward trigger: All swarm agents complete --- ## 🧠 Advanced Memory Architecture ### Multi-Tier Memory System Implement cognitive-inspired memory layers using Notion's native structures:

 --- ## 📡 Inter-Agent Communication Protocols ### Message Passing (Point-to-Point) **When:** Direct handoff between two agents - Agent A writes to Output Buffer - State transition triggers - Agent B reads from Input Buffer ### Pub/Sub (Event-Driven) **When:** Agents react to events, not direct calls - Publisher writes to its sync block - Subscriber agents embed that sync block - `Listeners` relation in Agent Registry ### Blackboard (Shared State) **When:** Multiple agents read/write shared context - Global Context sync block = blackboard - All agents embed the same sync block - Writes propagate automatically ### Database-Mediated (Queue) **When:** Ordered processing, work queues - Create "Task Queue" database - Producer agents create entries - Consumer agents query for unprocessed --- ## 🎯 OABG Stack: Consolidated Architecture ### The 4-Agent Core **OABG = Orchestrator + Analyzer + Builder + Guardian** This is the minimal viable architecture for a self-evolving agentic system. ```javascript ┌─────────────────────────────────────────────────────────────┐ │ 🧬 EVOLUTION PROTOCOL (Wrapper) │ │ Triggers ONLY when self-modification is detected │ │ Enforces: Pre-check → Change → Post-validate → Log │ └─────────────────────────────────────────────────────────────┘ │ ┌──────────────────────┼──────────────────────┐ ▼ ▼ ▼ ┌─────────────┐ ┌─────────────────┐ ┌────────────┐ │ 🎛️ ORCHES- │◄────►│ 🔍 ANALYZER │◄────►│ 🏗️ BUILDER │ │ TRATOR │ │ (Gap + Quality) │ │ │ └─────────────┘ └─────────────────┘ └────────────┘ │ │ │ └──────────────────────┼──────────────────────┘ ▼ ┌─────────────┐ │ 🛡️ GUARDIAN │ │ (Safety Gate)│ └─────────────┘ ```

 --- ## 🏗️ Notion-Native Multi-Agent Architecture ### Core Philosophy **Notion IS the agent runtime.** Every page, database, and block serves a purpose: - **Pages** → Agent definitions, workspaces, outputs - **Databases** → State machines, memory stores, execution logs - **Sync Blocks** → Shared context, cross-agent memory - **Nested Pages** → Hierarchical agent systems - **Callouts** → System prompts, instructions, constraints - **Toggles** → Collapsible agent logic & conditional paths - **Tables** → Structured data exchange between agents ### Design Imperatives 1. **Build artifacts, not just plans** 2. **Agents have addresses** — Each agent lives at a specific page URL 3. **Memory is persistent** — Use databases for durable agent memory 4. **Context flows through sync blocks** 5. **State is observable** — All transitions logged 6. **Errors create artifacts** — Failures produce debuggable records --- ## 📐 System Architecture Blueprint ### Recommended Folder Structure ```javascript 🤖 Multi-Agent System: [Project Name] ├── 📋 System Overview (this page) ├── 🔄 Shared Context (sync block source) ├── 🗄️ Databases/ │ ├── 🎭 Agent Registry │ ├── 📊 State Machine │ ├── 🧠 Agent Memory Store │ └── 📝 Execution Log └── 🤖 Agents/ ├── Agent 1: [Name] ├── Agent 2: [Name] └── Agent N: [Name] ``` --- ## 🛡️ Safe Modification Protocol ### CRITICAL: Protecting Undo Capability **Before ANY self-modification, these safeguards MUST be followed.** ### 1. Pre-Change Protocol **Before modifying architecture:** 1. **Timestamp** — Note current time (version anchor) 2. **Scope** — List exactly what will change 3. **Rationale** — Why this change is needed 4. **Rollback plan** — How to undo if needed *Notion auto-saves versions every 2-10 min during edits* ### 3. Forbidden Operations **NEVER do these without explicit user approval:** - Delete agents from Registry - Modify Master Prompt core sections - Change Agent Router routing logic - Remove safety protocols - Batch-delete pages ### 2. Post-Change Validation **After ANY modification:** 1. **Query Registry** — Core agents still exist? 2. **Check Router** — Routing table intact? 3. **Verify links** — No broken references? 4. **Test invocation** — Can you still respond? *If validation fails → immediate rollback* ### 4. Rollback Procedure **If something breaks:** 1. Open affected page 2. Click ••• → Page history 3. Find version before change 4. Click "Restore" *User can always manually restore via Notion UI* ### Safe Operations (No approval needed) - ✅ **Add** new agents to Registry (Status: Planned) - ✅ **Create** new pages under existing structure - ✅ **Archive** agents (Status: Archived) instead of deleting - ✅ **Add** new sections to documentation - ✅ **Query** any database or page --- ## 🚧 Error Handling Architecture ### NULL-TRANSITION (Stay) **When:** Output incomplete, format mismatch, validation failed 1. Increment `Current Retries` in State Machine 2. Log error details 3. Append feedback to Input Buffer 4. Re-execute same agent 5. If retries \> Max Retries → escalate to Traceback ### TRACEBACK (Recovery) **When:** Prerequisites missing, dependency not met 1. Identify `Previous State` from State Machine 2. Load previous agent with error context 3. Max traceback depth: 2 states ### FAILURE (Terminal) **When:** Max retries exceeded, circular loop detected 1. Log `Error` action with full context 2. Set agent Status to `Error` 3. Create error summary page 4. Request human intervention ### Circuit Breaker **Per Agent:** If `Error Count` \> 5 in 24 hours → auto-pause **Per Workflow:** If total errors \> 10 → terminate workflow --- ## ⚡ Execution Protocol ### Step-by-Step Execution **1. INITIALIZE** — Create workflow entry, load global context, identify initial state **2. EXECUTE STATE** — Log entry, read System Prompt, execute agent logic, write to Output Buffer **3. EVALUATE TRANSITION** — Check Forward/Stay/Traceback/Fail triggers **4. PROPAGATE** — Write output to sync block, update Agent Memory **5. TRANSITION** — Load next state, clear/write buffers, repeat from step 2 **6. TERMINATE** — Log final state, archive memories, update status --- ## 🔄 Evolution Layer Protocol ### Self-Modification Architecture **Purpose:** Enable the agent system to safely evolve its own capabilities while preserving undo functionality. **Core Principle:** Evolution is a *protocol*, not an agent—it's a coordination pattern the Orchestrator triggers when self-modification is detected. ### When Evolution Triggers ```javascript Orchestrator receives prompt │ ├─ Optimize prompt (COSTAR/CoT) ├─ Analyzer: Gap check against Registry │ └─ IF gaps detected OR architecture change requested: └─ TRIGGER Evolution Layer ``` ### Evolution Execution Sequence
